# Agent Prompt — Bestehen / Corpus Architecture — Stage 06 of 28
## Define the Source Registry, Discovery, and Acquisition Architecture

You are the acquisition/data-platform architect responsible for **Stage 06: Source Registry, Discovery, and Acquisition Architecture**.

Your job is to turn the settled source strategy into bounded, auditable discovery/acquisition architecture without equating accessibility with trust or rights. This is **architecture decision work, not production implementation**. Do not write crawler code, provider adapters, browser automation, deployment scripts, create accounts/resources/keys, configure dashboards, or make live fetch/provider calls.

## Project context

Corpus gathers broad German A2/B1 exam evidence for Bestehen / App. One owner operates it. Six independent axes must survive: provenance, authenticity/confidence, rights, difficulty/relevance, capability QA readiness, identity/metric independence. Source acquisition policy is not a trust decision and not a rights grant. Unknown is first-class. Every source location/file is untrusted and must pass security preflight before deep processing. Corpus is coverage-driven rather than an unbounded crawler.

## App implementation reuse and no-provisioning rule — mandatory

Read `Architecture/00-app-implementation-tooling-and-account-reuse-policy.md` and current App implementation provider handoff/runbook. This stage should not invent a second scheduler/control plane/network stack merely for acquisition. Start from the accepted App implementation family: existing two-VM Coolify + Pangolin, Node/TypeScript, PostgreSQL/pg-boss, GitHub Actions, R2 EU and Docker/Compose.

Prefer on-demand/batch acquisition jobs on existing infrastructure, PostgreSQL-backed scheduling/state, and existing private ingress/secret conventions. A dedicated crawler SaaS, managed browser service, queue service, proxy provider, new VM or new vendor account requires measured source-coverage/security need, incremental cost/ops, ADR and exit. Authenticated paid/private crawling remains out of launch scope.

This stage must not provision or run anything. Same-account reuse must still use least-privilege Corpus credentials/resources and never expose App learner data.

## Product/design truths not to reopen

Initial acquisition may include official/unofficial A2/B1/mixed sources. TELC is highest target relevance, not the only family. Launch does not include authenticated paid/private crawling. Owner-submitted URL/file does not bypass preflight or imply rights. Source Observations are preserved even when mirrors/dead locations are consolidated operationally. Discovery acceptance means “may enter acquisition,” not “trusted,” “permitted,” or “publishable.”

## Decisions this stage owns

1. Source registry concepts and state transitions for Source Family/provider/location/Observation/discovery candidate/acquisition policy.
2. Automated discovery versus owner-submitted URL/file/media intake; candidate creation without premature fetch.
3. Prioritization from provider/source value, coverage gaps, target relevance, format diversity and review cost without fabricating trust.
4. Host/path/source-family/content-fingerprint allow/block scopes, precedence and audit; no trust/rights side effects.
5. URL/location normalization while preserving redirects/mirrors/provenance.
6. Access behavior: robots/access-policy, rate limit, backoff, redirects, dead sources; Stage 12 owns network-security enforcement.
7. Mirror/dead-source preservation and preferred processing location vs provenance anchor.
8. Crawl/discovery budgets: bounded depth/pages/host/retries/concurrency/backfills; defer/stop states instead of hidden loops.
9. Source health vocabulary separate from trust/rights.
10. Revisit/change detection producing new observations/revisions, not rewritten history.
11. **Execution topology assessment:** compare on-demand jobs on reused App infrastructure against dedicated crawler workers/services; default to the former unless measured throughput/isolation requires more.
12. Define what, if anything, must remain always-on. Prefer scheduled/on-demand execution so Corpus adds minimal idle cost.

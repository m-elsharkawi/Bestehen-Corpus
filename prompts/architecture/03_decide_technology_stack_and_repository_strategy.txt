## Project context

Corpus is a single-owner A2/B1 exam-data/intelligence product. App consumes versioned eligible pattern intelligence and owns learner state/Readiness/original practice. Preserve the six independent truth axes, local uncertainty and capability-scoped publication. Corpus stores no learner data. All external input is untrusted. The operating posture is low-ops, deterministic/local/cheap-first, benchmark-qualified and replaceable.

## App implementation reuse and no-provisioning rule — binding default

Read `Architecture/00-app-implementation-tooling-and-account-reuse-policy.md` and current App implementation artifacts before comparing technology.

**Reuse the App operational ecosystem, not necessarily its programming language.** Current reusable infrastructure/account reality is GitHub/GitHub Actions; existing two-VM Coolify deployment/control boundary; Pangolin/Newt private ingress; PostgreSQL; Cloudflare R2 EU; Auth0 EU when auth is required; AWS SES Frankfurt when email is required; Gemini; OpenAI STT/TTS; Docker/Compose/OCI-compatible deployment; and existing owner secret-custody conventions.

The App implementation handoff says provider-service setup is accepted as repository/runbook work but is not yet proof every live external resource exists. Do not claim live resources from documentation alone.

### Python is first-class

**Do not start with a presumption that Corpus must use Node/TypeScript.** The owner explicitly allows the entire Corpus to be implemented in Python if that is the better approach. Python may be selected end-to-end without being treated as a reuse-policy exception, provided the chosen services are reproducibly containerized and deployable through the existing Coolify/Pangolin operating boundary.

Compare at least these coherent shapes:

1. **Python-first modular Corpus** — one primary Python runtime for API/control plane, workers and processing, with the simplest UI approach that preserves the owner-console design/accessibility contract; PostgreSQL/R2/provider-account reuse; Coolify deployment.
2. **TypeScript-first modular Corpus** — direct reuse of App Node/TypeScript/pnpm patterns; add no Python unless a bounded processor materially benefits.
3. **Hybrid** — one primary runtime plus a bounded second-language processor only when the measurable ecosystem/quality benefit outweighs two-runtime maintenance.

A Python-first design should explicitly evaluate mature document/PDF/image/OCR/ASR/data/ML ecosystems, typing/schema validation, async/background work, security patching, packaging, binary/native dependencies, testability, and container build/runtime cost. A TypeScript-first design should explicitly evaluate how much extra custom work or external-service dependence it creates for those same processing tasks.

The winner is the option with the lowest **total owner cost**, not maximum code reuse with App. Total owner cost includes development complexity, package/native-dependency maintenance, quality/benchmark fit, operational burden, recurring cash, variable processing cost, paid-provider dependence and exit risk.

### Provider/account burden of proof

For every external platform/provider use this order:

1. no extra service;
2. reuse the same App provider/account/billing relationship;
3. use a separate least-privilege Corpus resource inside that same account/infrastructure if isolation is needed;
4. introduce a new vendor/account/subscription only when a measured Corpus-specific blocker remains.

A new vendor/account must document why reuse fails, incremental recurring/variable cash cost, owner maintenance, security/privacy/rights effect, cheaper fallback, migration/exit and ADR. Temporary discounts are not sufficient reason.

“Same account” never means unsafe sharing of App learner data, broad credentials, one database schema, one bucket prefix or one API key.

## Decisions this stage owns

Settle every Stage 03 checklist item:

1. **Language/runtime selection.** Compare Python-first, TypeScript-first and hybrid with an explicit recommendation. If Python wins, choose a stable supported Python line and one simple environment/package/dependency workflow; do not add Node just for symmetry. If TypeScript wins, justify why Python’s processing ecosystem is not worth a second/primary runtime.
2. **Backend/control plane.** Choose the smallest server/application architecture for the owner UI, commands, jobs and internal APIs. Favor modular-monolith packaging over service sprawl.
3. **Operations UI.** Compare Next.js/React reuse with a simpler Python-native/server-rendered internal UI or other bounded option. Preserve design semantics/accessibility; minimize the number of ecosystems.
4. **Persistence.** Start from PostgreSQL reuse. Select a thin DB access/migration approach appropriate to the chosen primary language; do not force Kysely if Python is selected.
5. **Jobs.** Prefer PostgreSQL-backed durable jobs/state before Redis/managed queue. If Python is selected, choose a simple Python-compatible PostgreSQL job approach or application-owned job table/locking design rather than adding infrastructure merely to reproduce pg-boss.
6. **Object storage.** Start from same Cloudflare account/R2 EU boundary, normally separate Corpus bucket/resource/credential.
7. **Deployment.** Require container/OCI deployment on existing Coolify + Pangolin. Compare VM placement, on-demand/scheduled worker shapes and capacity before paying for another host/service.
8. **Identity/email.** Do not automatically add Auth0/SES. Compare Pangolin owner access alone vs reuse of Auth0 EU account with separate Corpus app/client if design/security requirements need it. Use no email if unnecessary.
9. **AI/media provider family.** Constrain later stages to reuse Gemini/OpenAI account families first; Polly remains `not_admitted` unless benchmarked.
10. **Repository strategy.** Choose simple private repository/module boundaries and avoid a build orchestrator unless measured need appears.
11. **Local dev/test.** Reuse Docker/Compose + PostgreSQL patterns and deterministic fakes. Live paid providers must not be required for normal local/CI.
12. **Dependency/native-tool policy.** Define pinning, licensing, vulnerability updates, reproducible binary/native installs, OCR/media system packages/model artifacts and container provenance.
13. **Observability.** Start with structured logs/health and existing GitHub/Coolify/VM/provider surfaces; no new APM/analytics/log SaaS at Stage 03.
14. **Upgrade triggers.** Define measurable thresholds for another VM, worker pool, search index, new queue/store, managed OCR/ASR or other complexity.

## Project context

Corpus is a single-owner A2/B1 exam-data/intelligence product. App consumes versioned eligible pattern intelligence and owns learner state/Readiness/original practice. Preserve the six independent truth axes, local uncertainty and capability-scoped publication. Corpus stores no learner data. All external input is untrusted. The operating posture is low-ops, deterministic/local/cheap-first, benchmark-qualified and replaceable.

### Burden of proof

For every stack/platform/provider choice use this order:

1. no extra service;
2. reuse the same App technology and existing owner account/billing relationship;
3. if isolation is needed, use a separate least-privilege Corpus resource inside that same account/infrastructure;
4. introduce a new vendor/account/subscription only when a measured Corpus-specific blocker remains.

A new vendor/account must document why the App implementation option fails, incremental recurring/variable cash cost, added owner maintenance, security/privacy/rights effect, cheaper fallback, migration/exit and a durable ADR. Temporary discounts are not sufficient reason.

**Do not confuse account reuse with unsafe resource reuse.** Default to separate Corpus database/schema/user, bucket/prefix credentials, API key/project or auth client where least privilege/right isolation needs it, while keeping the same provider account/control plane.

## Decisions this stage owns

Settle every Stage 03 checklist item:

1. **Reuse-first stack assessment.** Evaluate whether the App implementation stack can directly satisfy Corpus web/control plane, domain, jobs, storage, parsing orchestration and publication. Treat reuse as the default recommendation unless evidence identifies a blocker.
2. **Language/runtime.** Prefer Node/TypeScript for shared/control-plane work. A second language (for example Python) is allowed only as a bounded processor if OCR/document/media ecosystem or benchmark quality materially benefits; define IPC/artifact boundary and avoid a second web/backend platform.
3. **Operations UI.** Prefer the App’s Next.js/React/tooling family for the dense internal console unless a materially simpler solution meets design/accessibility/maintainability better. No second frontend ecosystem for convenience.
4. **Persistence/jobs.** Start from PostgreSQL/Kysely/pg-boss. Prove whether a separate Corpus database on existing infrastructure is enough; reject Redis/managed queues/new database providers absent measured need.
5. **Object storage.** Start from the same Cloudflare account/R2 EU boundary, normally with a separate Corpus bucket or tightly scoped resource/credential because Corpus rights/source bytes differ from App media.
6. **Deployment.** Start from existing two-VM Coolify + Pangolin. Compare placement/on-demand worker shapes, VM capacity and blast radius before paying for Render/Vercel/Railway/Fly/new VM/service. Stage 26 owns final environment operationalization.
7. **Identity/email.** Do not automatically add Auth0/SES. Compare Pangolin owner access alone versus reuse of the existing Auth0 EU account with a separate Corpus application/client if the design’s sign-in/second-factor/session requirements need it. If email is unnecessary, use none.
8. **AI/media provider family.** Do not select detailed routes yet, but constrain later stages to reuse Gemini/OpenAI account families first. Polly stays `not_admitted` by default.
9. **Repository strategy.** Choose simple private repository/module/package boundaries; use existing Node/pnpm/CI patterns where possible. No new build orchestrator absent measured need.
10. **Local development/test.** Reuse Docker/Compose, PostgreSQL and deterministic fakes; paid/live providers are never required for normal local/CI.
11. **Dependency/licensing/update policy.** Reuse App pinning/frozen-lock/supply-chain discipline where suitable; add bounded native tools only with licenses, versioning and reproducible installation.
12. **Observability.** Start with structured logs/health and existing GitHub/Coolify/VM/provider surfaces. Do not buy APM/analytics/log SaaS at Stage 03.
13. **Upgrade triggers.** Define measurable thresholds for extra VM, split worker pool, search index, alternate database, queue broker, specialized OCR/ASR service or new vendor.

## Cross-cutting requirements

- Background work must queue/defer/idempotently replay and preserve valid partial outputs.
- Untrusted parsing/model work must be isolatable without creating a service-per-stage architecture.
- App publication remains precomputed/versioned and learner-data-free.
- Every external service has a cheaper/no-service fallback or an explicit capability-held state.
- Tests/benchmarks must run without live paid calls.

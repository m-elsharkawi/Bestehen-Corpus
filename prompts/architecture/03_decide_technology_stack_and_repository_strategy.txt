## Project context

Corpus is a single-owner exam-data/intelligence product for German A2/B1 evidence; Bestehen / App consumes versioned eligible pattern intelligence and owns learner state, Readiness and original-practice generation. Architecture must preserve six independent truth axes—provenance, authenticity/confidence, rights, difficulty/relevance, capability QA readiness, and identity/metric independence—plus local uncertainty and capability-scoped publication. Corpus stores no learner data. Every external input is untrusted. The operating posture is low-ops, deterministic/local/cheap-first, benchmark-qualified and replaceable rather than fashionable or distributed by default.

## Product/design truths not to reopen

Do not select a design-tool runtime as production technology merely because the handoff uses `.dc.html`. Do not add microservices, streaming infrastructure, warehouse/lakehouse/vector databases, dedicated search engines or multiple managed stores just because they are common in “data platforms.” The product scale is roughly 20k–50k canonical Items, one owner, approximately `€25/month` normal cash envelope and approximately `€3/1,000 Items` target variable processing, subject to measured recalibration.

## Decisions this stage owns

Settle every Stage 03 checklist item:

1. **Language/runtime/backend comparison.** Compare credible stacks against document/media parsing ecosystem, type safety, background jobs, testability, operational familiarity/burden, security patch lifecycle, portability and packaging.
2. **Operations UI strategy.** Compare practical UI architectures that can implement the dense desktop-first, WCAG 2.2 AA owner console and persisted workflow state. Preserve design behavior; do not clone the design artifact runtime.
3. **Managed vs self-hosted posture.** Compare candidates for relational persistence, object/blob storage, scheduled/background execution and hosting. Treat search/vector/graph capabilities as optional needs to justify, not defaults.
4. **Repository strategy.** Choose monorepo/module/package organization, boundaries for core domain vs adapters/workers/UI/contracts, and how future isolation can occur without service sprawl.
5. **Local development.** Define reproducible local development and representative processing without requiring every paid provider.
6. **Dependency policy.** Define licensing, vulnerability/update policy, pinning/reproducibility, native/binary dependency handling, model/tool artifact provenance and export/exit requirements.
7. **Deployment candidates.** Identify feasible low-ops hosting/deployment shapes and their constraints, but leave final environment/CI/CD/release operationalization to Stage 26.
8. **Upgrade triggers.** State measured thresholds that would justify splitting services, adding a search index, separate worker pool, specialized managed media/OCR service or other complexity.

## Cross-cutting architecture requirements

- **Failure/recovery:** chosen components must support queued/deferred work, idempotent replay and preserving valid partial outputs.
- **Security/privacy/rights:** chosen stack must permit isolation of untrusted parsing/model work, least privilege and secrets separation; do not weaken this to reduce components.
- **App:** support precomputed/versioned publication without requiring a live learner-session dependency.
- **Cost:** show low/base/high recurring and variable cost for the recommended direction and cheaper fallback if a managed dependency exceeds budget.
- **Observability/testability:** require hooks for structured logs/metrics, reproducible tests and benchmark evaluation without selecting the full Stage 24/25 design yet.

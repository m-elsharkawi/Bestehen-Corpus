## Product invariants

Corpus is owner-only/internal, learner-data-free and can process asynchronously. App publication is immutable/bundle-first and App survives Corpus downtime. Product truth is not coupled to deployment status. Unsafe/incompatible releases fail closed without rewriting historical evidence.

## Decisions this stage owns

1. Define environment classes: local, CI, optional disposable preview, on-demand private staging, production/private owner use. Avoid always-on duplicate environments unless needed.
2. Define exact reuse topology across the existing Coolify controller/deployment VM(s) and Pangolin private ingress without embedding private addresses/names in Git.
3. Define container build/runtime contract for selected Python/TypeScript stack: pinned runtime/system packages, non-root/read-only where feasible, health/readiness, graceful shutdown, persistent-volume prohibition for authoritative data unless explicitly justified.
4. Define service decomposition at deployment level: minimum web/control plane and worker/process set; prefer one image/process family or one modular service where safe. On-demand/scheduled workers are preferred over paid/idle services.
5. Define PostgreSQL placement/isolation and migration runner using existing infrastructure if Stage 05 accepts capacity; separate Corpus DB/schema/user/backup credentials from App.
6. Define R2 Corpus buckets/resources/credentials inside existing Cloudflare account per Stage 05/23; production/staging separation where actually needed.
7. Define GitHub Actions CI/promotion and exact-commit release evidence. Reuse current GitHub account/workflow conventions; no separate release SaaS.
8. Define configuration/secrets: environment-scoped, least privilege, protected-ledger references, no secrets in build args/images/logs; reuse owner conventions.
9. Define deployment/promotion: fake/local first, exact commit, migration/compatibility gates, private staging rehearsal where needed, owner-controlled production promotion. Do not assume autodeploy is desirable.
10. Define release units for code, schema, taxonomy/rules, processor/model releases, benchmark and App publication; compatibility manifest rather than one mutable `latest`.
11. Define rollback/roll-forward and expand/contract migration; historical data/curated decisions cannot be rolled back by filesystem/image rollback.
12. Define backup/recovery integration and restore/delete-overlay replay from Stage 24.
13. Define phased activation/circuit flags server-owned and default closed for paid/model/publication capabilities; no feature-flag SaaS.
14. Define operational runbooks: deploy, pause workers, budget circuit, provider outage, takedown, restore, credential rotation/offboarding and App publication rollback.
15. Define measured capacity triggers for another VM, separate worker host, GPU capacity or new managed service.
16. Define current-price/capacity re-verification before any future provisioning; architecture does not authorize spend.

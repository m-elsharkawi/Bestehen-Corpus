# Agent Prompt — Bestehen / Corpus Architecture — Stage 05 of 28
## Define Data Ownership, Persistence, Storage, and Schema Evolution

You are the data architect responsible for **Stage 05: Data Ownership, Persistence, Storage, and Schema Evolution**.

Your job is to choose persistence/storage boundaries that preserve raw observations, curated decisions, derived intelligence, revisions, replay, rights/takedown semantics, audit and cost without premature polyglot infrastructure. This is **architecture decision work, not production implementation**. Do not create production migrations/DDL/ORM code, databases/buckets/accounts/keys, deployment configuration, dashboard changes or live provider calls.

## Project context

Corpus turns untrusted German A2/B1 source evidence into versioned rights-aware intelligence for Bestehen / App. It is one-owner and cost-bounded. Six axes—provenance, authenticity/confidence, rights, difficulty/relevance, capability QA readiness, and identity/metric independence—remain separately queryable/versioned. Observed, curated and derived state are not interchangeable. App receives pattern-first publication and sends no learner data.

## App implementation reuse and no-provisioning rule — mandatory

Read `Architecture/00-app-implementation-tooling-and-account-reuse-policy.md`, App provider handoff/runbook, App `.env.example`, and current App persistence/storage architecture.

Start from the existing implementation family: **PostgreSQL 18 + Kysely + pg-boss**, Cloudflare **R2 EU** via S3-compatible boundary, Docker/Compose, Coolify/Pangolin hosting boundary, and GitHub Actions. The default is to reuse the same technologies and owner provider accounts/control plane while keeping Corpus data logically isolated.

Preferred order:

1. PostgreSQL only for structured truth/jobs where it is sufficient;
2. same existing PostgreSQL infrastructure/host/account with a **separate Corpus database/schema/user** if security/capacity permits;
3. same Cloudflare account with a **separate Corpus R2 bucket or tightly scoped prefix/credential** when source-byte/rights isolation requires it;
4. new database/object/search/vector provider only with measured blocker, incremental cost/ops, ADR and exit.

Do not share App learner tables, DB credentials, object prefixes or broad storage keys with Corpus. Same-account reuse is a billing/control-plane optimization, not permission to mix data. Do not provision anything in this stage.

## Decisions not to reopen

Do not flatten six axes into one status. Do not overwrite observed source text with corrections. Do not delete duplicate observations to save space. Rights/takedown/suppression and physical deletion are distinct. Do not introduce warehouse/lakehouse/vector/search store before measured need.

## Decisions this stage owns

1. **Primary persistence strategy.** Evaluate PostgreSQL/Kysely reuse first and justify any deviation. State why search/vector/graph/warehouse are or are not needed at launch.
2. **Logical stores.** Define authoritative records vs projections/caches/artifact/blob storage and ownership.
3. **Cross-product isolation.** Decide logical/physical boundary between App and Corpus persistence: separate DB/schema/user/resource, credentials, backup namespaces and object prefixes while reusing existing account/infrastructure where safe.
4. **Identity/revisions.** Define stable IDs, immutable source observations, mutable/superseding interpretations and derived lineage.
5. **Observed/curated/derived separation.** Make edits append/supersede rather than erase.
6. **Transactional boundaries.** Define atomic vs eventually-consistent/stale-safe work.
7. **Content addressing.** Define source/artifact/media fingerprints, reuse, collision/integrity and takedown fingerprint interactions.
8. **Schema evolution.** Define structural/taxonomy/processing/analytics/App-contract migration/version policy.
9. **Retention/deletion/suppression.** Classify durable truth, reproducible derivative, ephemera/cache, suppressed content and physical deletion.
10. **Backup/restore foundation.** Reuse existing App backup/secret conventions where suitable; define Corpus-specific separation and what can regenerate. Stage 24 owns drills.
11. **Query needs.** Support Inbox/detail/audit, capability eligibility, reprocessing, analytics and App publication without semantic-denormalization shortcuts.
